# 轻量应用与部署

## 工程结构与接口

优先复用已有应用；新建时可采用 `public/` 静态页面、`worker/` API、`migrations/` 结构迁移、`tests/` 行为测试。同源前端/API 可减少跨域 Cookie 和 CORS 配置。哈希路由适合这种小型展示站，不强制引入前端框架。

| 接口类型 | 对外数据 | 权限 |
| --- | --- | --- |
| 公开目录 | 标题、封面、简介、状态、是否有下载 | 无需登录 |
| 注册/登录/退出/会话 | 网站自己的账号状态 | 按认证流程 |
| 作品下载 | 网盘地址、提取码、说明 | 有效用户会话，作品已上架 |
| 内容管理 | 完整资料及版本号 | 服务端验证站长角色 |
| 封面读取 | 经验证的小图片 | 公开，可缓存 |
| 封面上传 | 上传结果/封面地址 | 站长，限制格式和字节数 |

目录响应必须在服务端剔除私有下载信息。敏感 JSON 不放入静态目录，不通过前端隐藏实现权限；登录页和后台页面的 JS 可以公开，但数据与写入接口不能公开授权。

## 账号与管理员

- Cookie 使用 `Secure`、`HttpOnly`、适当的 `SameSite` 和 `Path`；`__Host-` 前缀 Cookie 不设置 Domain。服务端核对会话有效期和用户状态。
- 使用可信的密码哈希方案及验证过的实现。退出、改密、恢复账号要让应失效的会话失效。认证、下载、后台响应设置 `private, no-store`。
- 写接口检查请求来源和会话，并进行适量频率限制；用户名、会话令牌等索引减少 D1 扫描。
- 用户注册后，由用户提供要授权的用户名；只修改这个已存在账号的角色。新注册请求中的 `role` 不具有授权效力，不公开任何“初次站长”提权接口。
- 已有站点更新时，保持密码格式、用户 ID、会话表及登录密钥兼容。不为改域名或新增后台重置账号。

案例工程使用浏览器重 KDF 加服务端独立验证器来控制 Worker CPU。复用时保留完整参数和测试，不能只拿服务端较低迭代次数用于原始密码。客户端派生凭据仍等同认证秘密，只通过 HTTPS 传送且不记日志。新站不要未经评估就重新设计密码协议。[该思路的原始说明](https://doc.libsodium.org/password_hashing#server-relief)

## 后台内容保存

漫画站优先提供：封面、名称、作者（可选）、简介、状态「已完成/制作中」、网盘地址、提取码、发布开关；其余资料可折叠。尊重用户的实际字段要求，不把漫画状态套到其他产品。

- 保存写入 D1，公开目录从 D1 读取，新请求立即反映保存结果。不要让后台仅修改浏览器状态或临时 JSON 文件。
- 使用稳定作品 ID，更新不换 ID；显式控制上架状态，下架后读者下载接口也不返回链接。
- 更新带版本号，旧版本保存返回冲突，防止不同窗口互相覆盖。删除操作提供具体作品的确认，清理相关收藏，避免批量误删。
- 文本输出转义；网盘链接只接受完整 HTTPS 地址，拒绝脚本协议和带凭据 URL。提取码与 URL 分开保存。
- 初始化示例数据通过独立脚本执行。`INSERT OR IGNORE` 能保留现有同 ID 作品，但会重新插入已删除示例，因此也不能放进每次部署流程。

## 小封面存 D1 的适用范围

这是少量小图避免新增存储服务的取舍，不是通用文件托管设计。整本漫画和原图留在网盘；图片数量、流量或尺寸显著增加时重新评估存储架构。

案例的可复用起点：

- 原图接收 JPG、PNG、WebP，浏览器检查不超过 10 MB。
- 浏览器 Canvas 将最长边限制在 1200 像素，必要时降至 900/640，逐级压缩到 **100 KiB 以内**；后端不进行重型图片转码。
- 后端仍验证身份、MIME、文件特征和实际读取字节上限，不能信任文件扩展名或 Content-Length。拒绝 SVG/HTML；正确返回 Content-Type 和 `nosniff`。
- 使用内容哈希或不可变版本地址，公开封面可长期缓存；账号和网盘链接不共享缓存。
- 单独存封面，作品引用封面 ID。定时只清理超过宽限期且没有作品引用的封面，不扫描或误删正在使用的资源。

D1 原生绑定大字节数组会增加传输及序列化开销。案例用绑定的十六进制字符串和 SQL `unhex(?)` 保存 BLOB，读取 `hex(data)` 后还原字节，避免每个字节变为 JSON 数组元素。采用前验证运行时函数支持和字节往返一致性；值使用参数绑定，不拼接图片内容到 SQL。

100 KiB 是这个项目的应用限制，不是 Cloudflare 的平台上限或运行时保证。案例约 100 KiB 上传三次 CPU 为 14/8/5 ms，均成功；首次请求仍高于当时免费版标称 10 ms。应观测真实上传和登录的 CPU，不能把压缩完成当作所有请求都达标的证明。

## Wrangler 配置要点

在现有配置中保留真实值；新项目再填写自己的值。以下只是合并结构示意，不能原样发布：

```json
{
  "name": "YOUR_WORKER",
  "main": "worker/index.mjs",
  "assets": {
    "directory": "public",
    "binding": "ASSETS",
    "run_worker_first": ["/api/*"],
    "not_found_handling": "none"
  },
  "d1_databases": [{
    "binding": "DB",
    "database_name": "YOUR_DATABASE",
    "database_id": "YOUR_DATABASE_ID",
    "migrations_dir": "migrations"
  }],
  "routes": [{
    "pattern": "YOUR_HOSTNAME",
    "zone_id": "YOUR_ZONE_ID",
    "custom_domain": true
  }]
}
```

另按项目补充明确的 `compatibility_date`；用到 Node API 时检查 `nodejs_compat`。哈希路由可用示例的 404 策略，其他路由形式按应用调整。新 Zone 尚未激活时先部署 Worker，之后添加 Custom Domain。

只有首次新建需要创建 D1、生成登录密钥、设置 Secrets；已有项目先确认绑定而非重复创建。Wrangler 官方登录完成后使用该授权，不把 OAuth 令牌或 Secrets 打印出来。

常见命令形态（数据库绑定、脚本和路径以当前工程为准）：

```sh
npx wrangler login
npx wrangler d1 migrations apply DB --local
# 运行工程已有的构建和测试
npx wrangler deploy --dry-run
```

生产更新顺序：备份已有 D1 到私有位置 → 应用兼容的新结构迁移 → 仅在首次初始化时导入数据 → 发布代码 → 验证原账号与内容。备份可能暂时影响数据库服务，应选择合适时机并保存退出状态。

```sh
npx wrangler d1 export DB --remote --output PRIVATE_BACKUP_PATH
npx wrangler d1 migrations apply DB --remote
npx wrangler deploy
```

不修改已经应用的迁移文件，不在普通 HTTP 请求内自动建表。D1 请求若依赖刚发生的写入，采用合适的一致性会话；案例使用 `withSession('first-primary')`。一次 prepare 对应一条语句，多条用受控 batch。

## 发布验证与后续更新

有代表性的检查包括：匿名目录无私有链接；注册、登录、退出；普通账号访问后台被拒；站长保存后新请求看到资料；下载退出后失效；下架不可下载；不合法图片/URL 拒绝；旧版本编辑冲突；手机表单能操作。

涉及账号和数据保护时，优先用真实 workerd/D1 的集成测试。正式域名再做必要的验证，不用测试任意重建或清空生产库。测试记录使用唯一标识，结束时只清理这些记录；不要改用户密码来测试登录。

部署包采用源码白名单，包含依赖锁文件、配置、迁移、说明和必要测试；排除 `.dev.vars`、环境文件、令牌、数据库导出、`.wrangler`、`node_modules` 和本地账号状态。数据库备份单独保存，源码包不代表运行数据已备份。

域名、Worker、D1、密钥备份位置和管理账号分别记录在该项目私有部署说明；不要记录密钥值。通用技能不保存或复用账号专属标识。后续普通漫画资料通过后台保存，只有代码更改才重新部署。
