# 应用开发与部署

## 页面与工程

优先复用现有框架、样式和构建流程。新项目根据需求选择静态 HTML、静态生成器或前端框架；不要为了一个公开页面引入账号系统、数据库和大型运行时。

- 先落实页面结构、内容、导航与主要操作，再处理视觉细节。参考网站只用于理解布局和交互，使用用户有权使用的素材。
- 公共信息页面重视可分享的地址、页面标题和搜索可见性；按需求选择静态生成或服务端渲染。后台可采用单页应用，不统一强制哈希路由。
- 做好手机布局、图片尺寸、基础语义、表单标签和键盘操作。交互提供加载、空状态、成功和失败反馈。
- 文案直接表达页面用途；占位内容在预览中明确标识，正式发布前替换。不要给页面添加开发过程、部署架构或无关宣传文案。
- 纯静态资源可直接构建到 `public/` 或框架输出目录。增加动态逻辑时，可采用 `worker/`、`migrations/` 等结构，同源 `/api/*` 能减少跨域认证配置。

## 动态功能与权限

| 功能 | 数据处理 | 权限边界 |
| --- | --- | --- |
| 公开内容 | 接口只返回对外字段 | 未发布和私有字段在服务端剔除 |
| 访客表单 | 服务端校验并持久化，必要时限频 | 不公开提交记录、收件凭据或服务密钥 |
| 用户中心 | 查询当前会话对应的数据 | 不信任前端提交的用户 ID 或角色 |
| 受限资料 | 鉴权通过后返回所需内容 | 私有链接和个人数据不进入静态包或公共缓存 |
| 管理后台 | 持久保存、稳定记录 ID、明确发布状态 | 读写操作均在服务端验证权限 |

字段、状态和页面按当前业务定义，不复制其他项目的数据模型。后台保存必须落到持久存储；刷新页面、换设备和新请求应能看到结果。缓存更新策略要与这个要求一致。

并发编辑可能发生时使用版本号或等效机制，旧版本保存返回冲突。文本按输出上下文转义；富文本使用适当清洗。链接校验允许的协议，文件地址按需求限制为 HTTPS，拒绝脚本协议和带凭据 URL。

## 需要账号时

- 先确定是管理员登录、公开注册还是已有身份服务，不默认开放所有注册入口。选用适合当前运行时的可信认证实现。
- Cookie 使用 `Secure`、`HttpOnly`、适当的 `SameSite` 和 `Path`；使用 `__Host-` 前缀时不设置 Domain。服务端检查会话、用户状态和权限。
- 使用合适的密码哈希方案。验证退出、改密或账号恢复后的会话失效行为；敏感响应设置 `private, no-store`。
- 写接口按认证方式处理 CSRF 防护、来源检查和限频；用户名、会话等查询建立必要索引。
- 新注册请求中的角色字段不能赋予权限。只给用户明确指定的账号授权，不开放“首个用户自动管理员”的入口。
- 更新站点时保持密码格式、用户 ID、会话和密钥兼容。增加后台或更换域名不是重置账号的理由。

免费 Worker CPU 可能不适合某些密码派生实现。应评估认证库、运行时与架构，必要时说明免费方案的限制，不通过降低安全参数解决。已有特殊认证协议应完整保留并验证，不能抽取其中某一环节当作新站通用方案。

## 数据与文件存储

结构化数据可选 D1。为常用查询建立索引，避免无条件扫描；公开接口只选所需字段。结构迁移与示例初始化分开：普通部署不执行种子脚本，`INSERT OR IGNORE` 也可能重新插入用户已经删除的示例。

静态图片优先放在构建资源中。只有需要在线上传且数据量很小时，再评估将压缩图片存入 D1；大文件、高频上传或大量图片使用合适的外部文件存储，单独确认免费额度与开通条件。文件公开与否按需求决定。

小图片存 D1 的可选做法：

- 浏览器先调整尺寸并压缩，避免在 Worker 请求中进行重型转码。可将约 100 KiB 作为试算起点，再按质量、容量和 CPU 测量调整；这不是平台上限。
- 服务端验证权限、MIME、文件特征和实际字节数，不信任扩展名或 Content-Length。未实现安全处理时不接收 SVG/HTML 等主动内容。
- 公开图片用内容哈希或版本地址缓存，正确返回 Content-Type 与 `nosniff`；私有文件不能使用同样的公开缓存策略。
- 数据记录引用文件 ID。删除未引用资源前设置宽限期，避免清理刚上传、尚未保存关联的资源。

若 D1 二进制序列化成为瓶颈，可评估绑定十六进制字符串、SQL `unhex(?)` 保存 BLOB、读取 `hex(data)` 的方式。先验证当前运行时函数支持、字节往返一致性和实际开销；使用参数绑定，不拼接文件数据到 SQL。该取舍不应成为所有项目的默认存储方案。

## Cloudflare 配置

静态站可以只有 Assets 配置，例如：

```json
{
  "name": "site-static",
  "compatibility_date": "2026-11-07",
  "assets": { "directory": "./public" }
}
```

名称、兼容日期和输出目录根据当前项目确定；这是结构示例，不直接覆盖已有配置。动态站再增加 Worker 入口、所需绑定与路由，例如：

```json
{
  "name": "site-app",
  "compatibility_date": "2026-11-07",
  "main": "worker/index.mjs",
  "assets": {
    "directory": "./public",
    "binding": "ASSETS",
    "run_worker_first": ["/api/*"]
  }
}
```

只将必要路径交给 Worker。私有文件不能放在可绕过鉴权直接访问的 Assets 中；需要保护整段路径时调整路由并验证。单页应用的回退规则按实际路由设置，不让 API 错误返回首页 HTML。配置语义参见 [Static Assets 官方文档](https://developers.cloudflare.com/workers/static-assets/)。

需要 D1 时添加 `d1_databases` 的绑定名、数据库名称、真实 ID 和迁移目录。绑定自定义域名后，将 `routes` 中的主机名及 `custom_domain: true` 同步到工程；使用当前账号的实际配置，不复制示例或其他站点的资源 ID。用到 Node API 时核对运行时兼容设置。

只有首次新建才创建所需资源、生成密钥和初始化数据。已有项目先核对绑定。平台登录和 Secrets 使用官方机制，凭据不放进回复、日志或源码。

## 发布与迁移

以下命令是操作示例，使用项目锁定的依赖版本、实际路径和数据库绑定；没有数据库的站点跳过 D1 操作：

```sh
npx wrangler login
npx wrangler d1 migrations apply DB --local
# 执行项目的构建和相关检查
npx wrangler deploy --dry-run
```

新项目先创建必要资源并初始化；已有数据库更新前备份到受控位置，再应用兼容迁移、发布代码并验收。导出操作可能暂时影响服务，选择合适时机并确认完成状态。

```sh
npx wrangler d1 export DB --remote --output PRIVATE_BACKUP_PATH
npx wrangler d1 migrations apply DB --remote
npx wrangler deploy
```

不修改已应用的迁移文件，不在普通请求中自动建表。使用 D1 读副本时，对写后立即读取选择合适的一致性策略；跨请求需要时传递会话书签，不能只依靠前端重新请求假定一定读到新数据。参见 [D1 读副本与 Sessions API](https://developers.cloudflare.com/d1/best-practices/read-replication/)。

域名操作见 [域名与免费额度](domain-and-free-plan.md)，发布后的检查见 [验证与维护](validation-and-maintenance.md)。

源码包包含依赖锁文件、构建和部署配置、需要的迁移、说明及相关测试。排除环境密钥、数据库导出、平台登录状态、`.wrangler` 和 `node_modules`。备份单独保存；源码包不代表运行数据已备份。
